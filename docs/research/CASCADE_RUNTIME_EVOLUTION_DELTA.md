## 1. Scope & Objective

This document analyzes the exact **evolutionary delta** between the two foundational subsystems running in Krystal Stack today:
1. **The Multi-Model Cascade Subsystem (`krystal_kernel/cascade/`):** DAG compilation, epistemic routing, multi-model execution, contradiction detection, and closed-loop regret feedback.
2. **The AEP Transactional Subsystem (`krystal_kernel/aep_engine.py`, `llm_inference_governor.py`, `slovak_llm_adapter.py`):** L8 state machine transitions, invariant gates (`VITAL_MAX_HP == 6`), $\Delta S \equiv 0$ zero-dirty rollback, physical Win32 memory headroom validation, and cryptographic receipts.

The goal is to determine how to evolve the Cascade Planner from static heuristics into closed-loop planning using data **already generated by the system today**, without introducing speculative new architectures.

## 3. Four Concrete Evolutionary Deltas

### Delta 1: Closed-Loop Cascade Planner (Static $\to$ Empirical)
* **Current State:**
  In [`cascade_planner.py:348-356`](file:///c:/Users/dusan/Documents/GitHub/Krystal-stack-platform-framework/krystal_kernel/cascade/cascade_planner.py#L348):
  ```python
  lat = node_obj.estimate_latency({}) if node_obj else 15.0
  total += lat
  ```
  The planner uses a fixed 15.0 ms default or static node estimates.
* **Available Closed-Loop Data:**
  In [`closed_loop_adapter.py:240-270`](file:///c:/Users/dusan/Documents/GitHub/Krystal-stack-platform-framework/krystal_kernel/cascade/closed_loop_adapter.py#L240), `ClosedLoopCascadeFeedback.process_cycle()` already computes:
  ```python
  error_lat_ms = act_lat - exp_lat
  regret = max(0.0, error_lat_ms / max(1.0, exp_lat))
  ```
  And `CascadeExecutionTrace.node_results` contains the exact `latency_ms` measured for each node.
* **Evolutionary Action:**
  Allow `CascadePlanner.estimate_latency()` to query the historical moving average of `CascadeNodeResult.latency_ms` recorded in `ModelCascadeRuntime.trace_history` rather than returning the static 15.0 ms constant.

---

### Delta 2: ModelNode Evolution (Execute Primitive $\to$ Task-Aware Primitive)
* **Current State:**
  `ModelNode` is purely an execution primitive. It has an `infer(request)` method and static `spec: ModelNodeSpec`. It has no notion of:
  1. Priority (`TaskPriority`: P0 vs P3).
  2. Latency SLO budget (`slo_deadline_us`).
  3. Pre-emption or token scaling under load.
* **Evolutionary Action:**
  Wrap `ModelNode` execution in an outer task envelope (or task contract) that provides:
  - Input priority and maximum acceptable turnaround.
  - Ability to scale token generation (e.g. from 64 tokens down to 16 tokens) when the governor reports elevated bus pressure ($\mu_{\text{UMA}} \ge 0.50$).
  - Physical execution via `SlovakLLMAdapter` rather than synthetic mock text.

---

### Delta 3: Transactional Envelope for Cascade Plans
* **Current State:**
  `ModelCascadeRuntime.execute()` runs in user-space without transactional commit semantics. If a node fails or generates an unauthorized string, `CascadeExecutor` flags `AUTH_VETOED`, but there is no atomic rollback of session state.
* **Available AEP Infrastructure:**
  `AepTransactionalEngine.execute_transition()` ([`aep_engine.py:246`](file:///c:/Users/dusan/Documents/GitHub/Krystal-stack-platform-framework/krystal_kernel/aep_engine.py#L246)) already exists with complete invariant checking, state hashing, and $\Delta S \equiv 0$ rollback.
* **Evolutionary Action:**
  Directly wrap `GLOBAL_MODEL_CASCADE_RUNTIME.execute()` inside an `AepTransactionalEngine.execute_transition()` call with `workload=WorkloadType.INFERENCE`. On any veto or invariant failure, the candidate state is cleanly discarded, preserving $\Delta S \equiv 0$ and emitting an audit `AepReceipt`.

---

### Delta 4: Clock Domain Unification
* **Current State:**
  - `AepReceipt.timestamp_ns` and `CascadeTraceEvent.timestamp` use wall-clock `time.time()`.
  - `AepTransactionalEngine` and `SlovakLLMAdapter` compute latencies via monotonic `time.perf_counter_ns()`.
* **Evolutionary Action:**
  Standardize:
  - All durations, intervals, TTFT, and TPOT must use `time.perf_counter_ns()`.
  - Wall-clock `time.time_ns()` is used strictly for ISO-8601 audit timestamps in receipt headers.

## 4. Addressing the Core Research Questions

### Primary Question:
> **„Dokáže súčasný Cascade Planner prejsť zo statickej estimácie na closed-loop plánovanie len z dát, ktoré už produkuje?“**

**Preukázaný verdikt:**
**ÁNO.** Systém už dnes v `CascadeExecutionTrace` zachytáva:
- `latency_ms` pre každý uzol DAGu.
- `input_tokens` a `output_tokens` pre každý krok.
- `total_latency_ms` a `peak_memory_mb`.
- `authority_status` a `final_confidence`.

Prechod na closed-loop plánovanie nevyžaduje nový externý monitor ani nový zberný démon. Vyžaduje iba prepojenie:
$$\text{Trace History} \longrightarrow \text{Kĺzavý priemer latencií uzlov} \longrightarrow \text{CascadePlanner.estimate\_latency()}$$

### Subsidiary Question:
> **„Je už Model Node dostatočný task primitive pre LLM, alebo len execute primitive?“**

**Preukázaný verdikt:**
**Model Node je v súčasnom kóde výhradne EXECUTE PRIMITIVE.**
- Nemá životný cyklus (`CREATED`, `QUEUED`, `SCHEDULED`, `COMMITTED`, `REJECTED`).
- Nerozlišuje priority ani časové rozpočty úloh (SLO).
- Nevníma tlak zbernice UMA.
- **Dôsledok:** Aby mohol systém fungovať v režime „LLM task first“, musí byť `ModelNode` riadený nadradenou úlohou (`LLMTask`), ktorá definuje požiadavku, deadline a prioritu.
